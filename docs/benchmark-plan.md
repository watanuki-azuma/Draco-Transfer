# ベンチマークの手順

## 測定する段階

1. 符号化・復号の正しさ: 合成画像、単一/二重ビット誤り、並べ替え、重複、欠落。
2. 復号の処理時間: 合成画像で位置検出、既知形式の色判定、ECC/CRC、形式探索を分離。
3. 画像劣化への耐性: 拡縮、ぼけ、射影、色変化、圧縮、画面更新の混在。劣化処理と乱数seedを保存。
4. デジタル画面共有での全体転送。
5. 実機カメラでの全体転送。撮影と復号を別々に計測。

現行の `npm test` は1の一部、`npm run bench` は2。3〜5の測定機能と結果はまだない。

## 合成画像のベンチマーク

```sh
npm run bench -- --output baseline.json
```

9設定の最大ペイロードを同じ固定seedから作る。各設定はウォームアップ2回、測定7回。中央の50%値（p50）と最近順位法のp95を記録する。7回ではp95は最大値になるため、長時間の尾部遅延の推定とは扱わない。

- `bounds`: ピンク外枠の検索のみ。
- `sampleKnownMode`: 正しい形式・外枠を既知としてセルを色分類。
- `parseKnownCells`: 正しいセル列からECC・CRCを処理。
- `decodeAuto`: 自動位置検出と形式候補探索を含む現行の復号経路。

個別段階と全体は別々に測るので、p50同士を足して全体値としない。測定中の復号結果も入力バイト列と照合する。報告する計算上のKiB/sは、ペイロード容量÷単一画像の復号時間だけで算出した値。撮影・描画・欠落・ファイル検証の時間を含まない。

## 実機測定で残す条件

端末機種、OS、アプリ/ブラウザ版、カメラ、解析画像の形式・解像度・取得fps、露光、フォーカス、画面機種・サイズ・解像度・リフレッシュレート・輝度、距離、角度、照明、撮影中のコードの画素サイズ、CPU/GPU使用状況、継続時間、発熱による性能変化、ソースcommitを記録する。

同じカメラ録画・同じ補正後のROIを複数デコーダーへ入力できると、取得条件と復号方式を切り分けやすい。ただし録画の圧縮で結果が変わるため、実時間受信も別途測る。

## 全体転送の指標

- カメラ画像の取得数/秒、復号処理数/秒、正しく取得した新規ペイロード量/秒。
- 位置検出、補正、判定、ECC、ファイル復元の処理時間と待ち時間。
- 全体の成功率、欠落、訂正量、重複、再送量、開始から完了までの時間。
- 実効KiB/s = SHA-256検証済み原ファイルのバイト数 / 全転送秒数 / 1024。

全転送の開始は受信開始操作、終了はファイルのSHA-256検証完了とし、最初の有効フレームからの時間も副指標として残す。成功試行だけの速度を出す場合も失敗回数と打ち切り時間を併記する。

最初は1設定5試行と継続5分の測定を行う計画。短いファイルの瞬間値だけで継続性能を主張しない。

## 方式間比較

画面占有面積、撮影条件、表示速度、原ファイル、許容遅延をそろえる。訂正符号の追加量は記録し、同一量での比較と各方式を調整した比較を分ける。ランダムデータと圧縮済みファイルを含め、圧縮率による見かけの高速化を区別する。

新しい方式が合成画像で速いだけでは採用しない。撮影後の復元成功率と全体の実効速度も確認する。
