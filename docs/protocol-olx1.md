# OLX1: 初期の実験形式

状態: 実装済みのブラウザ試作。最終プロトコルではない。

## 画像

データ領域は N×N セル。Nは96、192、256。各セルは1、2、4ビットで、それぞれ白黒、4色、16色。外側に白い余白2セル、ピンクの外枠2セルを四方に配置する。画像全体は(N+8)×(N+8)セル。

RGBパレット、走査順、未使用セルの模様は [codec.js](../prototypes/browser/codec.js) を参照。左上から行順に並べる。各バイトを13ビットのSECDEDコードワードにし、コードワードの下位ビットからセルの下位ビットへ詰める。セル境界とバイト境界は一致しなくてもよい。

自動位置検出はピンク画素の外接矩形だけで行う。四隅の独立した検出マーカー、射影補正、回転補正、色補正は未実装。格子と色数は候補9通りを試し、ヘッダーとCRCが通ったものを採用する。

## ヘッダー

32バイト。複数バイトの整数はリトルエンディアン。

| オフセット | 長さ | 内容 |
|---:|---:|---|
| 0 | 4 | ASCII `OLX1` |
| 4 | 1 | version = 1 |
| 5 | 1 | bits/cell = 1, 2, 4 |
| 6 | 2 | N = 96, 192, 256 |
| 8 | 8 | ランダムなtransfer ID |
| 16 | 4 | 0始まりのフレーム番号 |
| 20 | 4 | 総フレーム数 |
| 24 | 2 | ペイロード長 |
| 26 | 2 | reserved = 0 |
| 28 | 4 | CRC32 |

CRC32は反転表現の多項式0xedb88320、初期値0xffffffff、最終XOR 0xffffffff。CRC欄をゼロにしたヘッダーとペイロード全体で計算する。ヘッダーを含めてSECDEDで符号化する。

## 誤り訂正

Hamming位置1〜12のうち、パリティは1,2,4,8、データは3,5,6,7,9,10,11,12。13番目が全体の偶数パリティ。データバイトの下位ビットからデータ位置へ格納する。

1コードワード内の単一ビット誤りを訂正し、二重ビット誤りを拒否する。それ以上の誤りに訂正保証はない。フレームCRC32と最終SHA-256で追加検証する。空間的なバースト誤りへの対策やインターリーブはない。

## ファイルストリーム

全フレームのペイロードを番号順につなぐと、次の内容になる。

1. UTF-8 JSON長: uint16（リトルエンディアン）。
2. JSON: `name`（ファイル名）、`size`（原ファイルのバイト数）、`sha256`（小文字の16進表記）。
3. 原ファイルのバイト列。

同じIDの重複フレームは無視する。全番号が揃ってから連結し、サイズとSHA-256を検証する。ACKや噴水符号はなく、欠落は送信の周回で補う。

送信ファイルの上限は32 MiB。SHA-256値も同じ経路から受け取るので送信者認証にはならない。暗号化、リプレイ防止はない。

## 容量

フレームのペイロード容量 = `floor(N² × bits/cell / 13) − 32`。

| N | 白黒 | 4色 | 16色 |
|---|---:|---:|---:|
| 96 | 676 B | 1,385 B | 2,803 B |
| 192 | 2,803 B | 5,639 B | 11,310 B |
| 256 | 5,009 B | 10,050 B | 20,132 B |

256×256・16色なら2 MiBのランダムデータは105枚に分割できる。ファイル名などのメタデータにより実際の枚数は変わる。容量は画像から読めることを前提にした値であり、実効転送速度ではない。
