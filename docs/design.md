# 方針と現在地

更新: 2026-10-11

## 何を試すか

専用の送受信GUIを使うなら、QR規格に合わせる必要があるのか。画面とカメラの能力に合わせた符号化にすると、容量や実効速度を上げられるのか。この問いを動く試作で検証する。

用途の確定は先送りする。近距離の汎用ファイル共有には既存の選択肢があるため、それらに勝つことを現時点の目標にはしない。接続を確立せず、見える画面からデータを回収できる性質を持つが、その価値も今後の検討対象。

遠距離では、映像を運ぶ経路が必要になる。そこでローカル処理なのは符号化と復号であり、転送経路そのものがオフラインになるわけではない。画面共有のデジタル画像と、実際に撮影したカメラ画像は別の条件として扱う。

## 高性能端末を使う仮説

高解像度の撮影、短い露光、画像処理の並列化、歪み・色補正、確信度を使った復号などに計算資源を投入する。どれが実効速度に効くかは測定する。

CPU/GPUの性能だけで通信速度が決まるとは考えない。libcimbarの性能文書は、より新しいCPUで復号を速くしても通常はカメラがボトルネックになると報告している。この報告をDracoの全端末に一般化せず、取得・処理・ファイル復元を分けて測る。[出典](https://github.com/sz3/libcimbar/blob/master/PERFORMANCE.md)

## 初期の選択

ブラウザ試作では実装が単純な色格子を採用した。1セルを色として判定し、Hamming SECDED、フレームCRC32、ファイルSHA-256で復元を検証する。これは比較用の出発点で、最終形式の決定ではない。

1バイトの8ビットを13ビットにするため、ECC部分だけで原データ比62.5%の追加ビットがある。符号率は8/13 ≈ 61.5%。さらにヘッダー、外枠、余白が必要。多色化で増やした容量のすべてがファイル容量になるわけではない。

実装上も、形式候補9通りのサンプリング、セルごとのパレット探索、ヘッダーの再復号、フレームごとのCanvas確保など、未最適化の処理がある。現行の測定値を方式自体の限界とは扱わない。

## 決めていないこと

- 最終的な変調方式、訂正符号、フレーム消失訂正。
- Androidネイティブかブラウザか、対象端末と表示機器。
- 必要な実効速度、距離、角度、消費電力、継続時間。
- 双方向通信、暗号化、認証、ライセンス。

既存方式の採用例は参考になるが、最適性やDracoの新規性の証明にはならない。まず公平な測定条件と再現可能な実験を作る。
