# 格子以外も含めた方式の比較

確認日: 2026-10-11

## 「コード復号が効率的か」を分ける

効率には複数の意味がある。原データ/表示面積、誤り訂正の追加量、CPU/GPUの処理時間、撮影後の復元成功率、電力、最終的なファイル転送速度を分ける。復号が軽くても撮影で情報が消える方式は速くならず、重い処理でも読める画像を増やせれば有利になる可能性がある。

QRが広く使われることや先行実装が存在することだけから、画面→カメラの大容量転送に最適とは結論しない。

## 一次資料で確認できた先行例

### libcimbar

色に加えて、タイル内の図形を画像ハッシュで識別する方式。単純な色セルとは異なる。実装には射影補正、インターリーブ、Reed–Solomon、wirehairによる噴水符号がある。セルの判定距離と位置ずれを使った復号順序の調整も記述されている。そのため「確信度を使う」こと自体を新規性とは扱わない。[設計資料](https://github.com/sz3/libcimbar/blob/master/DETAILS.md)

性能資料のmode Bでは、圧縮後4,689,084バイトを44秒、約852 kbit/sと報告。4 CPUスレッドのSnapdragon 625での値で、作者はカメラが通常のボトルネックと説明している。圧縮前のファイル容量、バースト速度、Dracoの未測定の理論値をこの数値と直接比較しない。[性能資料](https://github.com/sz3/libcimbar/blob/master/PERFORMANCE.md)

### PixNet（MobiCom 2010）

格子のセルを直接判定する代わりに、2次元の空間周波数へ情報を載せるOFDM系の研究。ぼけによる周波数ごとの減衰に応じた符号化などを扱う。論文の評価はDell 30インチ画面とCasio EX-F1、Nikon D3Xなどの撮影機器によるもの。論文の速度を現在のスマートフォンでそのまま再現できるとは考えない。[著者公開論文](https://people.csail.mit.edu/nabeel/pixnet-mobicom10.pdf)

### 画面–カメラ経路の容量研究（PerCom 2014）

射影歪みなどを含む容量モデルと既存実装の比較を扱う。符号化方式だけでなく、表示・撮影系の条件をそろえる必要があるという検討に使う。モデルの容量上限は実装の実効速度とは区別する。[著者公開論文](https://www.winlab.rutgers.edu/~gruteser/papers/aashok_PerCom2014.pdf)

会話中に挙がったPRISMFLOW、Optical File Transferは、正確なリポジトリと一次資料をまだ照合していない。公称値や機能を比較表の確定情報には入れない。

## Dracoでの比較候補

以下は実験案であり、優位性が実証済みという意味ではない。

| 候補 | 復号方法 | 比較で確認したいこと |
|---|---|---|
| 色格子（現行） | セル中心のRGBをパレット分類 | 単純さ、色変化・ぼけへの弱さ、密度と成功率 |
| 色＋図形タイル | 小領域の特徴・相関で識別 | 色だけより識別しやすいか、面積と計算量の増加 |
| 縞・位置・位相パターン | 相関やパターンのずれで識別 | 輝度中心で受信できるか、位置ずれ・モアレの影響 |
| 空間周波数方式 | FFTと周波数ごとの推定・復号 | ぼけ耐性、パイロット・振幅制約・処理コスト |
| 時間方向にも符号化 | 連続画像間の変化を解析 | 露光・画面更新・欠落に対する同期と遅延 |

特殊な模様だから容量が増えるとは限らない。読める空間周波数、区別できる色・輝度、使える時間変化へ情報をどう配分するかとして比較する。

## 高性能端末向けの検討

まず取得できる解析画像の解像度とfps、露光、継続時の性能を実測する。Androidの高速録画対応と解析用画像の高fps取得は同一ではない。高速セッションには出力先などの制約がある。[Camera2仕様](https://developer.android.com/reference/android/hardware/camera2/CameraConstrainedHighSpeedCaptureSession)

そのあと、ROI追跡、補正、色や図形の識別、確信度の利用、並列化を評価する。GPUを使うことや高級端末を指定することだけを成果指標にはしない。
